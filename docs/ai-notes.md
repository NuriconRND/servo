# AI 프로젝트 노트 (Claude Code 메모리 정본)

이 문서는 멀티GPU 비디오 월 프로젝트를 진행해온 Claude Code 세션의 **영속 메모리 스냅샷**이다.
(정본화 시점: 2026-07-17 — DComp 복합 콘텐츠 지원 사이클 + 애드온(티커 3원인/stylo 크래시/런타임 리사이즈) 전체 완료 시점.
초판: 2026-07-13, WR Native Compositor(DComp) 완료·푸시 직후. 이번 판은 그 이후 42커밋 분량의 여정을 포함한다.)
프로젝트의 전체 여정 — 근본원인 조사, 채택/기각된 설계, 실패 실험(재시도 금지 목록),
운영 함정, 검증 레시피 — 이 담겨 있다.

## 읽는 법
- 가장 작은 단위는 메모리 파일 1개이며 `<!-- memory/<파일명> -->` 주석으로 시작한다.
- 첫 파일(MEMORY.md)은 전체 인덱스다. 본문 중 `[[이름]]` 같은 표기는 같은 문서 안의 다른 절(해당
  이름의 메모리 파일)을 가리키는 상호참조다.
- 각 파일 상단의 YAML frontmatter(name/description/type)는 메모리 시스템용 메타데이터다.
- 절 안의 `§3-a` ~ `§3-y` 등은 시간순 작업 로그다. ★ 표시는 함정/재발방지 지식.

## 주의
- 로컬 경로(`D:\...`, `C:\Users\ilwoonam75\...`)와 장비 정보(RTX A5000, 20코어 등)는
  **작성 머신 기준**이다. 다른 환경에서는 경로를 자신의 것으로 치환해 읽을 것.
- 내용은 작성 시점의 사실이다. 파일/함수/플래그를 인용하는 부분은 현재 코드와 대조 후
  사용할 것.

## 다른 Claude Code 세션에서 이어받는 법
1. 그대로 읽기: 이 문서를 훑히면 배경지식으로 충분하다.
2. 메모리로 이식: 절 단위로 나눠 각 파일명대로
   `~\.claude\projects\<프로젝트-슬러그>\memory\` 에 저장하면 자동 메모리로 동작한다
   (슬러그는 자신의 프로젝트 폴더 경로에서 생성됨).

[[webrender-video-offload]]의 순수비디오 페이지 시나리오에 직결되는 이슈. 이벤트 폭주 메커니즘은 [[wall-mouse-rootcause]]와 동일 계열.

**2. winit 창 자동화 함정**: servoshell(winit)은 톱레벨 창 2개 — 실제 창(class `Window Class`)과 헬퍼(class `Winit Thread Event Target`). 시작 직후 `Process.MainWindowHandle`은 **헬퍼**를 반환할 수 있음 → 그걸 옮기면 "성공했는데 창은 그대로". EnumWindows로 class/title 확인 후 실제 창을 조작할 것.

**3-a. 45타일 fps 절벽 실측 (2026-07-08, 20코어 Ultra 7 265K + perf 페이지 ?log=1 스윕)**:

**목표 (2026-07-02 설정):** 다중 비디오 컴포지터 처리량 상향. 현재 이 머신(1920×1080, FHD30 H.264 타일)에서 **클린 60fps 실용 한계 ≈ 24~30 타일**; 40=marginal, 45=~30fps로 저하. 목표는 45~64 타일 60fps.

**근본 원인 (이번 세션에 확정 — 재조사 불필요):** WebRender가 각 `<video>`를 **제각각인 큰(1080p) 업로드 텍스처**로 그림 → **배칭 불가** → 레이어당 draw call(텍스처 바인드+유니폼), 이걸 **ANGLE가 GL→D3D11로 단일 컴포지터 스레드에서 번역** → CPU 커맨드 제출이 O(N). 측정: 40타일 `renderer.render()`≈17~20ms CPU(wr_render)인데 **A5000 GPU는 ~26%만**(GPU 바운드 아님), **업로드 <1ms**(I420 borrowed/zero-copy, 업로드 바운드 아님), 디코드는 별도 SW CPU. - NV12/BGRA로 YUV plane 바인드 감소 시도 → I420 borrowed/zero-copy 경로가 깨짐(videoconvert 필요, native-video 플래그가 협상 차단) → 업로드 350~700ms 폭발 → 훨씬 나쁨. **I420 borrowed가 최적.**
- HW 디코딩 → 사용자가 36+ 타일에선 배제.

Root cause + fix for the multi-GPU wall mouse bug (Task 2 in [[multigpu-next-session-tasks]]), found+VERIFIED 2026-06-14. Branch `multigpu-tiled-wall`. **DONE + COMMITTED + real-mouse-confirmed on both tiles:** waker fix = commit `5fcbcc560`, secondary-tile input routing = commit `6e1cfbb8a`.

**SYMPTOM:** On the wall at 60fps (animating WebGPU/canvas pages), winit delivers ~0 `CursorMoved`; the page never sees the mouse (flock doesn't follow cursor). Works at low fps.

**ROOT CAUSE (verified):** Servo's compositor `EventLoopWaker::wake()` (servoshell `desktop/event_loop.rs` `HeadedEventLoopWaker`) wakes the winit loop via `EventLoopProxy::send_event` = a **PostMessage** to the thread-event-target. In the Win32 `PeekMessage`/`GetMessage` priority order, POSTED messages outrank hardware INPUT (WM_MOUSEMOVE/clicks/keys). While animating, servo calls `wake()` ~**540/s** (≈10×/frame), so there is always a posted `AppEvent::Waker` ahead of the queued WM_MOUSEMOVE → input is perpetually starved → winit's PeekMessage never retrieves WM_MOUSEMOVE (measured `hook_mousemove/s=0` via a winit msg-hook) → ~0 CursorMoved. Low fps = sparse posts = input surfaces (the fps correlation). Affects ALL hardware input, not just mouse-move.

**FIX (verified working):** Suppress the waker's post while the app is animating, since `ControlFlow::Poll` already makes `about_to_wait` pump servo every iteration (the wake is redundant). Implemented as a shared `WakeCoalescer { animating, requested }` (in `event_loop.rs`) held by both the waker and `App`:
- `wake()`: set `requested=true`, then post ONLY if NOT `animating` (idle → post normally to wake the blocked loop).
- `App::set_control_flow_for_state`: `set_animating(is_animating)` FIRST, then `Poll` if `is_animating || requested` else `Wait`.
- `App::about_to_wait`: pump if `is_animating || take_requested()` (the owed pump for suppressed/idle wakes).
- The `requested`-flag + SeqCst ordering (`wake` does requested-store-then-animating-load; `set_control_flow` does set_animating-then-requested-load) guarantees no wake is lost across the animating→idle transition.

**VERIFIED 0->fixed** with an actually-moving synthetic cursor (see TEST PITFALL): pre-fix binary `mouseEv/s=0`, fixed binary `mouseEv/s=138-153`, `cursor_moved/s≈50`, page renders 60fps, both GPUs fine. Symptom: `D:\2_TechReview\20260606_multigpu_browser` (or its `servo\` subdir) refuses to rename — "something is running but unknown."

**Why:** Heavy use of background build-log monitoring (`tail -f ...servo/target/multigpu_logs/servo_build_*.log` and `grep -E "error\[|Compiling servoshell|Finished..."`) during servo builds. When the parent shell dies, `tail -f` and pipe-blocked `grep` keep running forever as orphans (parent `<dead>`). Their CWD stays inside the project folder, and Windows blocks renaming any dir that has a descendant held as a process CWD/open handle. ~32 such zombies had accumulated over 2 weeks (2026-06-11..23), some even tailing OTHER projects' logs (Omnivoice, ChurchPortal) but still locking this folder via CWD.

The remaining legit holders after cleanup: the live Claude Code session itself (its primary working dir IS this folder) + its MCP node/cmd servers + any open Windows Terminal/VS Code sitting in the folder. To actually rename: close those + exit the Claude session.

**How to apply:**
- Diagnose holders by reading each process's CWD from the PEB (no Sysinternals needed): P/Invoke `NtQueryInformationProcess` → PEB+0x20 = ProcessParameters → +0x38 = CurrentDirectory UNICODE_STRING (x64). Add-Type + scan MUST be in ONE PowerShell call (shell state doesn't persist between Bash/PowerShell tool calls — a separate-call type def silently makes every GetCwd throw → false "0 holders").
- Safe cleanup: kill only `grep.exe`/`tail.exe` whose parent PID is no longer alive. Verified safe (pure orphans). Don't touch live `claude`/`node`/`powershell` holders.
- Prevention: background monitors started during builds should be killed when done; or avoid `tail -f`/pipe-grep monitors whose writer can die and orphan them.
