**검증(verdict): RTSP feasible on bundled 1.22.8 — 플러그인 DLL은 이미 전부 있고, 등록(plugin list) 작업만 남았다.**

## Step 2: plugin_lists / gstreamer.py 등록 상태

실제 경로: `components/servo/gstreamer_plugin_lists/{common,windows,macos}.rs.in`, `python/servo/gstreamer.py`.

```
grep -n -iE 'rtsp|rtpmanager|gstrtp|udp' components/servo/gstreamer_plugin_lists/*.in
  common.rs.in:31:"gstrtp",
  common.rs.in:32:"gstrtpmanager",
grep -n 'gstrtsp|gstrtpmanager|gstrtp|gstudp' python/servo/gstreamer.py
  32:    "gstrtp",
  33:    "gstrtsp",
```

**브리프의 가정("현재 브랜치엔 없음")과 다른 실제 상태 — 부분적으로만 맞음:**

- **플러그인 목록(`common.rs.in`, 로드되는 `.dll` 플러그인)**: `gstrtp`, `gstrtpmanager`만 이미 등록됨(WebRTC 작업에서 들어온 것으로 보임). **`gstrtsp`(RTSP 소스/싱크 플러그인 자체)와 `gstudp`(RTP-over-UDP 전송)는 등록 안 됨.** `windows.rs.in`/`macos.rs.in`에도 없음.
- **`gstreamer.py`의 `GSTREAMER_BASE_LIBS`**: `gstrtp`, `gstrtsp`가 이미 있다 — 하지만 이건 **베이스 공유 라이브러리**(`gstrtp-1.0-0.dll`, `gstrtsp-1.0-0.dll` — 플러그인들이 링크하는 SO 의존성) 목록이지, 플러그인 자체가 아니다. `windows_dlls()`가 이 목록으로부터 자동으로 `-1.0-0.dll` 접미사를 붙여 계산하므로 별도 조치 불필요.
- **`GSTREAMER_WIN_DEPENDENCY_LIBS`(외부 FFmpeg/기타 서드파티 DLL 명시 목록)**: RTSP 관련 추가 항목 불필요 (gstrtsp/gstudp 플러그인은 avformat 등에 의존하지 않음).

**Task 3에서 실제로 해야 할 일 (정정된 범위):**
1. `components/servo/gstreamer_plugin_lists/common.rs.in`에 `"gstrtsp"`, `"gstudp"` 두 줄 추가 (기존 `"gstrtp"`/`"gstrtpmanager"` 옆).
2. `gstreamer.py`의 `GSTREAMER_BASE_LIBS`/`GSTREAMER_WIN_DEPENDENCY_LIBS`는 **변경 불필요**(gstrtsp 베이스 라이브러리는 이미 목록에 있고 자동 계산됨).
3. mach가 이 두 플러그인 dll을 패키징 대상에 새로 추가하도록 재빌드 시 DLL 복사 스텝이 다시 돌아야 함(목록이 바뀌면 마커 파일 로직상 재복사됨).

**최종 검증(verdict): RTSP feasible on bundled 1.22.8 — DLL은 전부 있음, 필요한 건 `common.rs.in`에 2줄 추가뿐(플러그인 자체 등록). BLOCKED 아님.**

## Step 3: `htmlmediaelement.rs` 병합면 조사

### `components/script` 크레이트의 unit test 가능 여부

- `grep -rl '#\[test\]' components/script/` → **0건**. 이 크레이트에는 기존 `#[test]` 함수가 전혀 없다.
- `components/script/Cargo.toml`은 워크스페이스 루트의 `js = { package = "mozjs", ... }` (SpiderMonkey 전체)를 의존성으로 링크한다. `cargo test -p script`를 실행하면 test harness 빌드가 mozjs 전체를 다시 링크해야 하며(디버그 빌드 기준 매우 느림), 기존에 아무도 이 방식을 쓴 적이 없다는 사실(0건)이 이를 방증한다.
- 비교: 이 저장소의 실제 unit test 관례는 CLAUDE.md에도 나오듯 `cargo test -p servoshell wall_layout --lib`처럼 **더 가벼운 크레이트**(`servoshell`)에 로직을 놓고 테스트한다.

**검증(verdict): mozjs-infeasible — script 크레이트 자체에 `cargo test` unit test를 새로 추가하는 건 인프라 관례에도 없고 mozjs 링크 비용 때문에 비현실적이다. Task 2/3의 `is_extended_container_type`/`is_direct_uri_scheme` 류 순수 함수는 (a) 가능하면 더 가벼운 크레이트로 추출하거나, (b) 그럴 수 없으면 런타임 스모크(probe 페이지 + 로그 확인)로 검증한다. 후자를 기본 전제로 한다.**

### 라이브 RTSP 엔드포인트

`rtsp://...`로 도달 가능한 서버가 현재 이 조사 환경에는 없다 — **이는 사용자 환경의 몫이므로 이번 태스크에서 프로비저닝하지 않는다.** 로컬에서 기동하는 방법(기록만, 미실행):
- **mediamtx** (구 rtsp-simple-server): 단일 바이너리, `mediamtx.exe` 실행 후 `ffmpeg -re -i rtsp_testsrc.mp4 -c copy -f rtsp rtsp://localhost:8554/test`로 이 태스크가 복원한 mp4를 그대로 퍼블리시 가능.
- **gst-rtsp-server** 예제(`test-launch`): `test-launch "( filesrc location=rtsp_testsrc.mp4 ! qtdemux ! ... )"` 형태로 동일 파일을 서빙 가능. 번들 1.22.8에 필요한 rtsp/rtp/rtpmanager/udp 플러그인이 이미 있으므로(Step 1) 클라이언트(Servo)뿐 아니라 로컬 서버 기동용으로도 같은 GStreamer 설치를 재사용할 수 있다.

**OPEN QUESTION (사용자에게):** 실제 `rtsp://` 엔드포인트(로컬 mediamtx/gst-rtsp-server든, 외부 카메라/NVR이든)를 Task 3 런타임 스모크 전까지 준비해 둘 것인지 확인 필요. 없으면 Task 3의 RTSP 런타임 스모크는 "자산/엔드포인트 대기"로 표시하고 나머지(플러그인 등록, dispatch 로직)만 우선 진행한다.

## Step 1~4 종합 결론

- **RTSP: feasible on bundled 1.22.8.** DLL 전부 존재, `common.rs.in`에 `gstrtsp`/`gstudp` 2줄 추가만 하면 등록 완료. base lib 쪽(`gstreamer.py`)은 이미 준비돼 있어 손댈 필요 없음(브리프의 "DLL 없으면 블로킹" 시나리오는 해당 없음).
- **htmlmediaelement.rs 병합면:** 겹치는 곳 2군데(`update_media_state`, `create_media_player`) — 모두 인접 블록 수준, Task 3 실작업 시 수동 병합 후 리뷰 필요 지점으로 표에 명시함.
- **script 크레이트 테스트:** unit test 전례 없음 + mozjs 링크 비용 → Task 2/3은 순수 로직도 런타임 프로브로 검증하는 걸 기본 전제로 한다.
- **테스트 자산:** rtsp_testsrc.mp4 복원 완료. jxl/avi 샘플 기존 확보. tiff/exr/qoi/mkv/wmv는 미확보 — 해당 스모크는 "자산 대기". 라이브 RTSP 엔드포인트는 사용자 환경 몫 — OPEN.
