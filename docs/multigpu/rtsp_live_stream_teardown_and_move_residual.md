# RTSP 라이브 스트림: DOM 제거 시 teardown, 그리고 "이동 중 잔상" (2026-08-20)

winit_wall 릴리스 빌드를 받은 동료로부터 두 건의 피드백이 왔다.

1. **`<video>` 엘리먼트를 DOM에서 제거해도 RTSP 세션이 ESTABLISHED로 남는다.**
2. **영상의 잔상이 월에 간헐적으로 남는다** — 추가 피드백으로 조건이 좁혀졌다: 별도의 control
   페이지가 output 페이지의 레이아웃을 실시간으로 밀어 넣는 구성에서, **rtsp `<video>`의 표출
   위치를 실시간으로 바꾸는 동안** 잔상이 "남았다가 사라졌다를 반복"한다. Chrome은 안 그런다.
   ★output 페이지의 변경은 winit_wall이 마우스 이벤트를 받아서 일어나는 것이 아니다.★

①은 원인 규명 + 수정 + 실측 검증까지 끝났다. ②는 **이 개발 장비에서 재현되지 않았지만**
(6개 구성·약 800프레임), 동료 쪽 추가 실측으로 트리거가 밝혀졌다: **픽처 캐시 타일 수가
슬라이스당 2장 이상일 때만 발생한다.** 타일 크기를 화면 크기와 같게 하면 사라진다 — §2 첫 절.

---

## 1. 증상 ① — 제거해도 스트림이 안 끊긴다 (해결)

### 원인

HTML 스펙의 "remove an element from a document" 단계는 **pause만** 한다
(`MediaElementMicrotask::PauseIfNotInDocument` → `internal_pause_steps`). 분리된 엘리먼트를 다시
문서에 넣으면 이어서 재생할 수 있어야 하니 스펙으로서는 옳다.

파일 재생에서는 이 비용이 0에 가깝다 — 일시정지된 파이프라인은 파일 핸들 하나를 쥐고 있을 뿐이다.
그러나 `rtsp://`에서는 **카메라 세션 하나**가 비용이다:

- pause는 GStreamer 파이프라인을 `PAUSED`에 둔다.
- RTSP는 `NULL`로의 전이에서만 TEARDOWN을 보낸다.
- 따라서 서버는 프로세스가 죽을 때까지 세션을 ESTABLISHED로 유지한다.

카메라는 동시 세션 수가 몇 개로 제한되고, 비디오 월은 이런 엘리먼트를 하루 종일 만들고 버린다.

### 수정

`components/script/dom/html/htmlmediaelement.rs` 에 `stop_live_stream_on_removal()` 을 추가하고
`PauseIfNotInDocument` 마이크로태스크의 `internal_pause_steps()` 직후에 호출한다.

- **직접-URI 스킴(`rtsp`/`rtsps`)이고 `dom_video_network_uri_enabled` 가 켜졌을 때만** 동작한다.
  나머지는 스펙의 pause-only 동작 그대로다.
- ★player를 stop 할 뿐 **버리지 않는다**★(`reset_media_player` 와 다른 점). 엘리먼트를 다시
  삽입하고 `play()` 하면 그대로 살아난다 — 라이브 스트림에서 "이어서"란 재접속을 뜻하므로
  잃을 재생 위치가 애초에 없다.

### 검증 (실측)

`tests/html/rtsp_teardown_probe.html` (t=8s 에 `element.remove()`, t=12s 에 마지막 JS 참조 해제)
를 표준 플래그 세트로 돌리면서 밖에서 `netstat` 를 폴링:

| | 수정 전 | 수정 후 |
|---|---|---|
| 카메라로의 TCP 연결 (제거 후) | 런 끝까지 `ESTABLISHED` | t≈9.2s 에 **1 → 0** |

## 2. 증상 ② — 이동 중 잔상 (트리거 규명: 슬라이스당 타일 수 > 1)

### ★2026-08-20 추가 피드백 — 픽처 타일 크기가 범인이다★

동료가 `gfx_wr_picture_tile_size` 를 **3840x2160(= 4K 실기 화면 크기 그대로)** 으로 바꾸자
**잔상이 사라졌다.** 표준 세트의 `1920x1080` 은 3840x2160 서피스를 **타일 4장**으로 쪼개고,
3840x2160 은 **타일 1장**으로 만든다. 즉 트리거는 해상도가 아니라 **슬라이스당 타일 수 > 1** 이다.

이 프로젝트 구성에서 `gfx_dcomp_mode=surface` 는 `StorageMode::SurfaceOnly` 라 서피스가 절대
스왑체인으로 승격되지 않는다(승격 게이트가 `mode == Hybrid`). 전부
`IDCompositionVirtualSurface` 이고, 가상 서피스는 **다시 그리지 않은 타일의 픽셀을 그대로
유지한다** — 그게 픽처 캐시의 목적이다. 타일이 1장이면 매 프레임 그 한 장이 갱신되므로 낡은
픽셀이 남을 자리가 없다. 타일이 여러 장이면 갱신되지 않은 타일이 옛 픽셀을 계속 들고 있고,
비디오가 비우고 간 자리가 그런 타일에 걸리면 그게 잔상이다.

**권장 조치: `--pref gfx_wr_picture_tile_size=display`.** 이 pref 는 리터럴 `WxH` 말고
`display` 를 받고, 그 뜻이 정확히 "타일 크기를 그 타일 창 실제 크기에 맞춘다 = 슬라이스당
타일 1장" 이다(`components/paint/painter.rs` `resolve_wr_tile_size` 의 doc 주석). 하드코딩된
`3840x2160` 과 달리 해상도가 섞인 월에서도 맞고, 레이아웃을 바꿔도 다시 적을 필요가 없다.
표준 플래그 세트의 `gfx_wr_picture_tile_size=1920x1080` 을 `display` 로 바꾸는 것을 제안한다.

아래 §"무엇을 쟀나" 이하는 이 피드백을 받기 전 조사 기록이다. 결론(이 장비 미재현)은 그대로
유효하고, **왜 미재현이었는지**를 위 사실이 설명한다: 이 장비의 뷰포트는 1920x1080 이라 표준
세트의 `1920x1080` 이 이미 "타일 1장"이었고, 일부러 960x540 으로 쪼갠 런에서도 네 타일이 매
프레임 전면 더티로 다시 그려져(로그 실측) 낡은 타일이 생기지 않았다.

### 무엇을 쟀나

`tests/html/rtsp_move_residual_probe.html` — 스크립트 타이머로 엘리먼트를 움직인다(마우스 입력
없음: 동료의 구성이 그렇고, winit_wall은 애초에 입력 좌표 리매핑을 하지 않는다). 세 구간:
리사주 스윕(뷰포트 중앙을 계속 가로지른다) → 500ms 대점프 → 1px 넛지.

판정은 눈이 아니라 픽셀이다. 프로브의 `<video>`는 마젠타(`#c56cf0`) 테두리를 두르므로 **살아 있는
엘리먼트의 위치를 화면에서 직접 특정**할 수 있고, 그 사각형 바깥의 밝은 덩어리 = 잔상이다.
지연(스미어)은 별도로 테두리 바깥 40px 링의 밝은 픽셀 비율로 쟀다.

★판정기는 양성 대조군으로 검증한 뒤에 믿을 것★ — 첫 판정기는 **마젠타 픽셀 전체의 바운딩
박스**를 "살아 있는 엘리먼트"로 잡았는데, 잔상은 당연히 자기 테두리까지 통째로 남으므로 두
사각형을 한 박스가 삼켜 그 사이가 전부 검사에서 빠졌다. 실제 프레임에서 영상 사각형을 오려
다른 자리에 붙인 인공 잔상 이미지로 재보니 **한 건도 잡지 못했다.** 고친 판정기는 마젠타 픽셀을
연결 성분으로 **군집화**해 "마젠타 사각형이 2개 이상이면 잔상"으로 본다(대조군 통과). 아래
숫자는 전부 고친 판정기로 다시 센 값이다.

관측은 데스크톱 스크린샷으로 한다 — `gfx_dcomp_mode=surface` 에서는 `--capture` 프레임버퍼
readback 이 순백(mean 255)으로 돌아온다(실측). WebRender 가 DComp 서피스에 그리기 때문이다.

### 결과: 6개 구성 · 약 800프레임 · 잔상 0 · 지연 0

|---|---|---|---|

같은 런에서 마젠타 사각형 **안쪽**의 밝기 평균·표준편차가 프레임마다 변한다 = 영상이 실제로

### 이 결과가 배제하는 것

- 이동 방식(레이아웃 `left/top` vs `transform`) 자체의 문제가 아니다.
- 픽처 캐시 타일 경계를 가로지르는 것 자체가 원인이 아니다 — 타일이 4장이어도 매 프레임 전부
  다시 그려지면 잔상이 없다. 문제는 경계가 아니라 **갱신되지 않는 타일**이다.
- 3840×2160 가상 뷰포트 지오메트리 자체가 원인이 아니다.
- external 서피스가 콘텐츠보다 늦게 배치되는 "한 프레임 지연" 가설도 아니다 — 지연이 있었다면
  테두리 밖 링에 영상 픽셀이 삐져나왔을 텐데 500프레임 내내 정확히 0이었다.

### 남은 차이 = 다음에 봐야 할 곳

이 장비의 물리 출력은 1920×1080 한 장이고, 동료는 **3840×2160 실기 모니터** 한 장이다. 가상
뷰포트만 4K로 키운 런은 엔진 쪽 지오메트리만 같아질 뿐 DWM/DComp 가 실제 4K 오버레이를 합성하는
경로는 재현하지 못한다. 그리고 동료의 output 페이지 구조(스케일 컨테이너 유무, 비디오 개수,
겹침·클립)는 이쪽에서 알 수 없다.

### 컴포지터 로그가 알려준 것 — 왜 여기서는 나올 수가 없었나

`SERVO_DCOMP_DEBUG=1` + `RUST_LOG=paint=info` 로 같은 프로브를 돌려 3만여 줄을 받았다. 두 가지가
결정적이다.

**(1) 비디오는 external 서피스로 승격되지 않는다.** 표준 플래그 세트에서 만들어진 서피스는 딱
둘(`create_surface id=0 opaque=true`, `id=1 opaque=false`)이고, 매 프레임 합성되는 것은 `id=0`
하나뿐이다 — `add_external_surface`/`place_external_visual` 계열은 **한 줄도 찍히지 않았다.**
즉 비디오는 자기 DComp 비주얼을 갖지 않고 페이지 콘텐츠와 같은 서피스(가상 서피스)에
래스터된다.

→ 이것으로 "비디오 오버레이가 콘텐츠보다 한 프레임 늦게 따라온다" 계열의 설명은 전부 탈락한다.
   Chrome 이 드래그 중 오버레이를 강등해 회피하는 그 문제는 여기서 애초에 일어나지 않는다.

**(2) 이 장비에서는 타일 더티 사각형이 항상 "전면"이다.**

```
bind surface=NativeSurfaceId(0) tile=(0,0) dirty=(0,0)-(1920,1080)   ← 1920x1080 타일, 매 프레임
bind ... tile=(0,0)/(1,0)/(0,1)/(1,1) dirty=(0,0)-(960,540)          ← 960x540 타일 4장, 전부 전면
```

두 타일 크기 모두, 모든 프레임에서 더티가 타일 전체다. **전면 더티는 곧 "모든 타일이 매 프레임
다시 그려진다"는 뜻이고, 그러면 낡은 타일이 생길 수가 없다** — 이동 잔상이 이 장비에서
800프레임 내내 0이었던 이유가 이걸로 설명된다(동료 쪽 타일 수 발견과 정확히 맞물린다).

WebRender 는 타일당 더티 사각형을 **하나**(그 타일 무효화의 합집합)만 준다. 그래서 처음에는
"프로브가 좌상단 문구를 매 프레임 갱신하니 합집합이 (문구 ∪ 옛 비디오 ∪ 새 비디오) ≈ 타일
전체가 된 것"이라고 봤고, 그걸 끄는 `?quiet=1` 을 넣어 다시 쟀다. **결과는 여전히 10,502/10,502
전면 더티였다.** 즉 이 장비에서 전면 더티가 나오는 이유는 페이지 쪽 갱신 때문이 아니다
(컴포지터 능력치는 `max_update_rects` 기본값 1 이라 부분 더티를 못 받는 구성도 아니다).
왜 항상 전면인지는 아직 모른다 — 다만 **여기서 부분 Present 가 아예 발동하지 않는다**는 사실은
확정이고, 그래서 이 장비에서는 잔상이 나올 수가 없었다.

### 부분 Present 가설은 폐기 — 남은 것은 "갱신되지 않은 타일"

한때 유력했던 설명(콘텐츠 스왑체인의 부분 Present 가 낡은 픽셀을 남긴다)은 두 가지로 폐기한다.
첫째, `gfx_dcomp_mode=surface` 는 `StorageMode::SurfaceOnly` 라 서피스가 스왑체인으로 승격되지
않는다 — 승격 게이트가 `mode == Hybrid` 다. 부분 Present/`StaleTracker`/`self_copy_catchup` 은
전부 스왑체인 arm 의 코드라 이 구성에서는 실행되지 않는다. 둘째, 동료 쪽 해결책(타일 크기를
화면 크기로)은 부분 Present 와 무관하고 **타일 수**만 바꾼다.

남는 설명은 가상 서피스의 정상 동작 그 자체다: **다시 그리지 않은 타일은 옛 픽셀을 유지한다.**
타일 1장이면 매 프레임 그 한 장이 갱신되므로 낡을 자리가 없고, 여러 장이면 비디오가 비우고 간
자리를 담당하는 타일이 그 프레임에 갱신되지 않을 때 옛 프레임이 그대로 보인다. 다음에 그 타일이
갱신되면 사라진다 = "남았다가 사라졌다를 반복".

즉 근본 수정은 "그 타일이 왜 무효화되지 않는가"(WebRender 픽처 캐시 무효화) 쪽에 있고, 운용
회피책은 슬라이스당 타일을 1장으로 만드는 것이다(위 `=display` 권장). 회피책이 확실하므로
근본 수정은 급하지 않다 — 다만 타일 1장은 무효화 입도를 잃는 대가가 있어(매 프레임 화면 전체
재도색) 큰 월에서 비용을 재볼 필요는 있다.

### 4K 실기에서 한 번에 좁히는 절차

프로브를 표준 플래그 세트로 돌리되, **아래를 한 번에 하나씩만** 바꿔 A/B 한다. 각 런은 표준 세트를
그대로 두고 env 하나 또는 pref 하나만 다르다.

```powershell
# 기준선 (표준 세트 그대로)
winit_wall.exe --wall-all-tiles --wall-layout <4K layout> <표준 플래그 전량> `
  "file:///.../tests/html/rtsp_move_residual_probe.html?src=rtsp://user:pass@host:port"
```

| 순서 | 바꿀 것 | 사라지면 범인은 |
|---|---|---|
| 1 | `--pref gfx_wr_picture_tile_size=display` | **슬라이스당 타일 수 > 1 — 실측으로 확인됨(동료 3840x2160)** |
| 2 | `--pref gfx_dcomp_mode=off` (GL 경로로) | DComp 네이티브 컴포지터 경로 전체 |
| 3 | `$env:SERVO_DISABLE_VIDEO_IMMEDIATE_COMPOSITE=1` | 비디오 프레임 도착마다 하는 즉시 재합성 |
| 4 | `--pref media_d3d11_enabled=false` | D3D11 제로카피 업로드 경로 |

1번이 이미 동료 쪽에서 확인됐다 — 다른 증상이 아니라면 2~4번은 볼 필요가 없다.

`$env:SERVO_DCOMP_DEBUG=1` 을 얹으면 프레임마다 `[dcomp-dbg] add_surface … clip=…` 이 찍힌다.
★단, **`$env:RUST_LOG='paint=info'` 를 같이 줘야 한다**★ — 이 로그는 `log::info!` 이고 기본 필터가
info 를 버린다. 그리고 크레이트의 `[lib] name` 은 `paint` 다(패키지명 `servo-paint` 가 아니다).
같은 이유로 `SERVO_DCOMP_DEBUG` 만 주고 아무 줄도 안 나오는 것은 "이벤트가 없다"는 뜻이 아니다 —
실제로 이쪽에서 그 함정에 한 번 빠졌다. DComp 가 실제로 붙었는지는 로그가 아니라 `--capture`
결과로 확인하는 게 확실하다: DComp 가 붙으면 프레임버퍼 readback 이 **순백(mean 255)** 으로
나온다(WebRender 가 DComp 서피스에 그리기 때문). 이번 5개 런 모두 순백이었다 = DComp 경로가
실제로 동작 중이었다.

로그에서 볼 것은 `[dcomp-dbg] bind ... dirty=` 한 줄이다 — 전면이면 부분 Present 무관, 부분이면
위 예측대로다.

프로브의 질의 파라미터:

- `?src=` (필수) — 자격증명이 붙으므로 페이지에는 하드코딩하지 않는다.
- `?move=transform` — 레이아웃 대신 트랜스폼으로 이동.
- `?resize=1` — 이동하면서 크기도 함께 변화(스왑체인 재생성 경로).
- `?quiet=1` — 매 프레임 갱신되는 문구를 끈다(타일 더티 합집합을 비디오만으로 좁히려는 시도).
