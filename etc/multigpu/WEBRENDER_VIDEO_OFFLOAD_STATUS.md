## 무엇을 쟀나

- **Baseline B**: `video_grid_6x6_perf.html` = N개 진짜 `<video>` (N WebRender 레이어). I420 borrowed/zero-copy 업로드.
- **V1** (낙관 상한): `video_collapse_ceiling.html` 공유 텍스처 1개를 N quad, 단일 WebGL canvas = **단일 WebRender 레이어**. 업로드 0 → 순수 draw-call 접기 비용만.
- **V2** (보수 상한): 타일별 텍스처 N개 + 매 프레임 `texImage2D` 재업로드(RGBA). 업로드 포함, **실제 C2보다 무거움**.
- 각 × dom{0,1} × N{30,40,45,64}. 계측: `SERVO_LOG_PRESENT_CADENCE` + `RUST_LOG=warn,paint=info`. 정상상태 중앙값(앞 10 샘플 워밍업 제거). PresentMon 물리 present 교차확인은 이번엔 생략.

### 읽는 법 / 주의
- **신뢰 신호 = `rAF fps` + `present/s`** (max_gap 보조). 60Hz vsync 상한이므로 60이 실질 만점.
- `wr_render`/`wr_update` 열은 **>16ms 프레임(느린 프레임)만 로깅**된 값의 중앙값 → 60fps 유지 config에선 정상 프레임(<16ms)이 아예 안 잡히고 **기동 시 드문 outlier 1~2개**만 남는다. 그래서 v1의 `wr_render=122.9`/`wr_update=143` 같은 값은 정상상태가 아니라 시작 스톨 1개다. **fps/present로만 판단**할 것.
- `baseline dom0 n64`의 `present/s='-'`: present-cadence 샘플이 워밍업 컷 이하라 파서가 신뢰불가로 비움(rAF=35.8은 유효).
- **dom0 ≈ dom1** 전 구간에서 거의 동일 → DOM 오버레이 합성 비용은 무시 가능(메모리의 "DOM은 잘 확장" 재확인). 혼합 video+DOM은 성능 문제 아님, C2에선 병합 *정합성*만 관건.

## 판정 (go/no-go): **GO — C2 착수 정당화(강)**

- **V1이 N=30~64 전부 clean 60fps** → "N개 비디오를 **1레이어/1패스로 접으면** 병목이 사라진다"는 가설을 강하게 검증. 목표(45~64@60fps) 달성 가능.
- **Baseline은 ~40타일 넘어가면 붕괴**(45→40fps, 64→34fps) → 병목은 **WebRender의 레이어당 오버헤드**(N 레이어를 매 프레임 개별 처리)이지, 업로드/디코드/GPU가 아님을 재확인. (baseline의 `wr_update`가 작음 = 업로드는 이미 zero-copy.)
- **V2가 5fps로 baseline보다도 나쁨** → **naive per-frame RGBA 재업로드는 치명적**. 이게 C2의 **핵심 설계 제약**을 준다: C2는 절대 CPU 왕복/재업로드를 하면 안 되고, **비디오의 이미 상주하는 zero-copy I420 borrowed 평면을 그대로 재사용**해야 한다. 그 평면은 이미 컴포지터 안에 있으므로(baseline이 그걸로 zero-copy 합성 중) C2가 남길 일은 **V1이 싸다고 증명한 draw-call 접기뿐** → V1의 60fps@64에 근접할 것으로 기대.

### V1이 C2의 공정한 프록시인 근거
V1은 공유 텍스처 1개를 쓰지만, 실제 C2는 N개의 **서로 다르되 이미 상주하는** 평면을 바인드한다. `bindTexture`×N 비용은 무시 가능(어떤 배치 렌더러든 하는 일). V1/C2를 가르는 진짜 비용인 **업로드는 borrowed 평면 경로에서 이미 ~0**(V2가 증명: 업로드를 넣으면 5fps로 폭락). 따라서 V1은 C2가 도달 가능한 천장(1레이어 + N textured quad, 1패스)을 공정하게 근사한다.

## 다음 단계 — C2 구현 세션

접근 C2 (Servo 내부 컴포지터 fast-path)를 별도 세션에서 설계·구현:
1. painter/컴포지터가 디스플레이 리스트에서 **z-연속 + 공간적으로 서로 안 가리는 비디오 이미지 레이어 런**을 감지.
2. 그 런의 각 비디오 **borrowed I420 평면(3-plane, zero-copy)** 을 자체 YUV→RGB 셰이더 + quad로 **1개 중간 서피스에 1패스 합성** → WebRender엔 이미지 1개(또는 그 런 자리에 1레이어)로 넘김. **재업로드/CPU 왕복 금지.**
3. DOM이 끼는 경계에서 병합을 쪼갬(정합성 유지, 이득만 감소). 순수 격자면 전부 병합.
4. **디코드 천장 별도 확인**: V1/V2엔 디코드가 없다. C2는 baseline과 동일한 N개 SW 디코드 부하를 물려받으므로, C2 실전 천장 = min(컴포지터≈V1의 60fps@64, N개 서로 다른 SW 디코드 CPU 천장). 64 distinct 디코드가 CPU 벽인지 C2 세션에서 측정.

폴백(접근 A, DirectComposition 네이티브 오버레이)은 **불필요** — 접기론이 검증됐고 C2가 훨씬 작다.
